> **상태** : 구현됨 (작업 트리, 인게임 테스트 전). 결정 사항 D1 ~ D8은 기본안이다. 확정하면 표시를 지운다 (10장)
> **기준** : 브랜치 `origin/feature/systemRefactoring`, 커밋 `cd1e9c3` + 작업 트리 (`FacilityC`, `Lever` 수정분 포함)
> **목적** : 설비 A · B · C의 고장 여부를 **고장 플래그**로 관리한다. 두 가지 동작을 만족시킨다.
> 1. **수리를 완료하면 장치를 초기화한다.** 슬라이더는 기본값(`initialValue`)으로, 버튼은 전부 회색으로 돌아간다.
> 2. **고장이 아닐 때 장치를 조작하면, 장치는 반응하지만 게임에는 영향이 없다.** 버튼 색이 바뀌고 슬라이더가 움직이며 소리도 나지만, 고장 · 타이머 · 패널은 그대로다.

## 1. 배경

### 지금 생기는 문제

| # | 증상 | 원인 |
| --- | --- | --- |
| 1 | **정상일 때 슬라이더가 움직이지 않는다** | 슬라이더 값 변경 → `FacilityB`가 "고장 아님"을 알림 → `FacilityManager`가 수리 완료로 보고 `Clear()` 호출 → `slider.ResetState()`가 값을 되돌리고 `_dragCamera = null`로 드래그를 끊는다 |
| 2 | **정상일 때 버튼을 누르면 고장이 된다** | `FacilityA.IsFault()`가 "버튼 ≠ 목표(전부 회색)"로 계산된다. 누르면 곧바로 고장으로 판정되어 `GameManager`가 타이머를 켠다 |
| 3 | 조작할 때마다 알림이 간다 | A는 클릭마다, B는 드래그 중 매 프레임 `OnFacilityInteracted`를 보낸다. `FacilityManager`는 매번 패널 갱신 이벤트를 보내고, "고장 아님"이면 `Clear()`까지 부른다 |
| 4 | 수리 때 드래그가 어중간하게 끊긴다 | B 수리 순간 `ResetState()`가 슬라이더 쪽 드래그만 끊는다. 컨트롤러는 여전히 잡고 있다고 알고 있어서, 마우스를 뗄 때까지 이동이 막힌다 |

### 근본 원인
- A · B는 고장 여부를 **장치 상태로 계산**한다 ("장치 ≠ 목표"). 그래서 목표가 없는 정상 상태에서도 장치를 건드리면 판정이 바뀐다.
- 수리 후 초기화를 **`FacilityManager`가 외부에서** 한다 (`_facilities[facilityID].Clear()`). 그래서 "고장 아님" 알림이 올 때마다, 정상 상태에서도 초기화가 일어난다.

### 현재 코드

| 위치 | 현재 |
| --- | --- |
| `Facility` | `IsFault / MakeFault / Clear / Initialize` 전부 abstract. 고장 상태 필드 없음 |
| `FacilityA` | `IsFault()` = 버튼 ≠ 목표. 클릭마다 `OnFacilityInteracted(IsFault(), id)`. `isFault`는 인스펙터 확인용 |
| `FacilityB` | `IsFault()` = 목표가 있는 슬라이더 중 범위 밖이 있음. 값 변경마다 알림. `Clear()` = `slider.ResetState()` |
| `FacilityC` | 이미 고장 플래그 방식. 정상일 때 당기면 알림 없음 |
| `FacilityManager.OnFacilityInteracted` | `OnFacilityStatusChanged(!isFault)`, "고장 아님"이면 `_facilities[facilityID].Clear()` |
| `FacilitySlider.EndDrag` | 놓을 때도 `OnValueChanged`를 보낸다 |

## 3. 핵심 설계 : 고장 플래그와 공통 수리 흐름 (D1)

### 상태 전이

```
            MakeFault()                      장치 변경 + 목표 달성
  [정상] ─────────────────────▶ [고장] ─────────────────────────▶ [정상]
    ▲   목표 생성, isFault=true    │     isFault=false, 장치 초기화,     │
    │                             │     수리 알림 (한 번)               │
    │   장치 변경 : 장치만 반응     │   장치 변경 : 목표 미달성이면        │
    └── (설비 · 게임 영향 없음) ────┘   아무 알림 없음                   │
                                                                      │
  Clear() : 어느 상태든 isFault=false + 장치 초기화 (재시작용) ◀──────────┘
```

- 고장 여부는 **`isFault` 플래그만** 본다. 장치 상태는 "목표를 달성했는가"를 검사할 때만 쓴다.
- 목표 달성 검사는 **고장 중일 때만** 한다. 정상일 때 장치를 조작해도 플래그는 바뀌지 않는다.
- 알림은 **수리 완료(고장 → 정상) 한 번만** 보낸다 (D2).

### Facility 기반 클래스 (안)

```csharp
public abstract class Facility : MonoBehaviour
{
    public Action<bool, int> OnFacilityInteracted;      // 시그니처 유지 (D8). 이제 수리 때만, isFault = false로 온다

    [SerializeField] protected int facilityID;

    [Header("Observation")]
    [SerializeField] protected bool isFault;           // A · B · C에 있던 같은 이름 필드를 여기로 모은다

    public int FacilityID => facilityID;
    public bool IsFault() => isFault;                   // abstract → 공통 구현

    public abstract void Initialize();

    // 고장 발생. 이미 고장이면 무시
    public void MakeFault()
    {
        if (isFault) return;
        GenerateGoal();
        isFault = true;
    }

    // 강제로 정상 + 장치 초기화. 재시작용
    public void Clear()
    {
        isFault = false;
        ResetDevices();
    }

    // 하위 클래스가 장치 변경 때마다 부른다
    protected void OnDeviceChanged()
    {
        if (!isFault) return;                 // 정상 : 장치는 이미 반응했다. 설비에는 영향 없음
        if (!IsGoalReached()) return;         // 고장 중, 아직 미달성 : 알림 없음

        isFault = false;
        ResetDevices();                       // 수리 완료 → 장치 초기화
        OnFacilityInteracted?.Invoke(false, facilityID);
    }

    protected abstract void GenerateGoal();   // 새 목표 만들기 (현재 장치 상태와 겹치지 않게)
    protected abstract bool IsGoalReached();  // 목표 달성 검사
    protected abstract void ResetDevices();   // 장치 초기화 (+ 목표 해제, 목표 표시 끄기)
}
```

- `IsFault`, `MakeFault`, `Clear`는 **이름과 호출 방식이 그대로다.** `FacilityManager`, `MainPanelDisplay`, `GameManager`는 호출 코드를 바꾸지 않는다.
- 하위 클래스의 `isFault` 필드를 지우고 기반 클래스로 옮긴다. 이름이 같아서 씬 · 프리팹에 저장된 값이 그대로 이어진다. (하위 클래스에 같은 이름을 남기면 Unity가 "같은 필드가 여러 번 직렬화된다" 오류를 낸다.)
- 초기화(`ResetDevices`)를 **알림보다 먼저** 한다. 알림을 받은 쪽(패널 등)이 이미 정리된 상태를 본다.
- **설비가 스스로 초기화하므로**, `FacilityManager`는 더 이상 `Clear()`를 부르지 않는다 (D7). 그 결과 "`facilityID` = 배열 인덱스" 의존도 이 경로에서 사라진다.

## 4. 설비별 변경

### FacilityA (버튼)

| 훅 | 동작 |
| --- | --- |
| `Initialize` | 기존과 같음 (버튼 초기화, `OnButtonPressed` 구독, 목표 전부 회색, 가이드 표시). 끝에 `isFault = false` |
| 버튼 클릭 (`OnButtonClicked`) | `OnDeviceChanged()` 호출만. 직접 알림을 보내지 않는다 |
| `GenerateGoal` | 목표를 무작위 생성 → 가이드 표시. **현재 버튼 상태와 같으면 다시 뽑는다.** `16` 하드코딩 대신 `facilityButtons.Length` |
| `IsGoalReached` | 모든 버튼 `Status == 목표` |
| `ResetDevices` | 모든 버튼 `Clear()`(회색), 목표 전부 회색, 가이드 갱신 |

- 정상일 때 누르면 : 버튼 애니메이션 · 색 순환 · 클릭음은 그대로 난다. `OnDeviceChanged`에서 바로 돌아가므로 고장 · 타이머 · 패널에 영향이 없다.
- 수리 순간 : 마지막으로 누른 버튼을 포함해 16개 전부 즉시 회색이 된다. `FacilityButton`의 색 변경 코루틴은 0.25초 뒤 `_status`(이미 회색)로 다시 칠하므로 충돌하지 않는다.

### FacilityB (슬라이더)

| 훅 | 동작 |
| --- | --- |
| `Initialize` | 기존과 같음. 끝에 `isFault = false` |
| 값 변경 (`OnSliderValueChanged`) | `OnDeviceChanged()` 호출만 |
| `GenerateGoal` | 슬라이더마다 `SetTarget(MakeTarget(slider.Value), tolerance)` (기존 `MakeTarget` 그대로) |
| `IsGoalReached` | 모든 슬라이더 `IsInRange` |
| `ResetDevices` | 모든 슬라이더 `ResetState()` (값 `initialValue`, 목표 해제, 끄는 소리 정지, **드래그 종료**) |

- 정상일 때 끌면 : 손잡이가 움직이고 끄는 소리가 난다. 목표가 없으므로 '철컥'은 나지 않는다. 설비에는 영향이 없다.
- 수리 순간 : 마지막 슬라이더가 범위에 들어가면 '철컥'이 나고, 곧바로 4개 모두 기본값으로 돌아가며 잡고 있던 드래그가 끝난다 (5장).
- `FacilitySlider.EndDrag`가 보내는 `OnValueChanged`는 이제 해가 없다. 값이 바뀌지 않았으므로 목표 달성 여부도 같다. 다만 불필요하므로 지운다 (D6).

### FacilityC (레버)

| 훅 | 동작 |
| --- | --- |
| `Initialize` | `lever.OnPulled += OnLeverPulled`, `isFault = false` |
| 당김 (`OnLeverPulled`) | `OnDeviceChanged()` 호출만 |
| `GenerateGoal` | 할 일 없음 |
| `IsGoalReached` | `repairChance >= 1 || Random.value < repairChance` (한 번 당길 때 판정 한 번) |
| `ResetDevices` | 할 일 없음. 레버는 스프링이라 스스로 올라온다. 강제로 되돌리면 손잡이가 순간이동한다 (「설비 C 레버 구현 계획」 4장) |

- 지금 동작과 결과가 같다. 공통 구조에 맞추는 것뿐이다.
- 실패한 당김에 대한 알림(`OnFacilityInteracted(true, …)`)은 없어진다 (D2).

## 5. 수리 순간의 드래그 종료 (D4)

B는 드래그 도중(값이 바뀌는 순간)에 수리가 완료되므로, 장치 초기화가 **잡고 있는 슬라이더**까지 되돌린다. 이때 드래그를 양쪽에서 깔끔하게 끝내야 한다.

| 방안 | 내용 | 판단 |
| --- | --- | --- |
| **A. 장치가 드래그를 끝내고, 컨트롤러가 알아챈다** | `IDraggable`에 `bool IsDragging { get; }` 추가. `FacilitySlider.ResetState()`가 드래그를 끝내면 `FirstPersonController.UpdateDrag`가 매 프레임 확인하다 `StopDrag()` | **채택.** 장치가 컨트롤러를 몰라도 된다. 이동 잠금 · 시점 감도가 바로 풀린다 |
| B. 놓을 때까지 초기화를 미룬다 | 수리 판정은 즉시, 슬라이더 초기화는 드래그가 끝난 뒤 | 초기화 시점이 설비마다 달라진다. 구현이 복잡하다 |
| C. 지금처럼 둔다 | 슬라이더만 드래그를 끊고, 컨트롤러는 마우스를 뗄 때까지 잡은 상태 | 마우스를 뗄 때까지 걷지 못하고 시점도 느리다. 이유를 알 수 없어 버그처럼 느껴진다 |

### 변경

| 파일 | 변경 |
| --- | --- |
| `IDraggable` | `bool IsDragging { get; }` 추가 : "지금 잡혀 있는가" |
| `FacilitySlider` | `public bool IsDragging => _dragCamera != null;` |
| `FirstPersonController.UpdateDrag` | 커서 검사 옆에 `if (!_dragTarget.IsDragging) { StopDrag(); return; }` 추가 |

- `StopDrag()`는 `EndDrag()`를 한 번 더 부른다. `EndDrag`는 이미 끝난 상태에서 불려도 안전해야 한다 (지금 코드는 안전하다 : 카메라 null, 소리 정지뿐. D6에 따라 `OnValueChanged` 호출을 지우면 더 확실하다).
- 수리 순간의 흐름 :

```
Update (컨트롤러) → slider.Drag → SetValue
   ├ CheckRange → 범위 진입 '철컥' (snapSource. ResetState가 멈추지 않으므로 끝까지 들린다)
   └ OnValueChanged → FacilityB.OnSliderValueChanged → OnDeviceChanged
        └ 목표 달성 → isFault=false → ResetDevices → 4개 모두 ResetState (드래그 종료)
                    → OnFacilityInteracted(false) → FacilityManager → 패널 · 게임 흐름
다음 프레임 Update (컨트롤러) → UpdateDrag → !IsDragging → StopDrag → 이동 · 시점 감도 복구
```

## 6. FacilityManager 변경

| 위치 | 지금 | 변경 |
| --- | --- | --- |
| `OnFacilityInteracted(bool isFault, int id)` | `OnFacilityStatusChanged(!isFault)` + "고장 아님"이면 `_facilities[id].Clear()` | `OnFacilityStatusChanged(!isFault)`만 남긴다. **`Clear()` 호출을 지운다** (설비가 스스로 초기화) |

- 이제 이 함수는 수리 완료 때만 불리고 `isFault`는 항상 false다. 시그니처는 유지한다 (D8).
- 정상 설비 조작이 알림을 보내지 않으므로, 버튼을 눌러 타이머가 켜지던 문제(1장 #2)가 사라진다.

## 7. 조작별 결과 (완성 후)

| 상황 | 장치 반응 | 설비 · 게임 |
| --- | --- | --- |
| 정상, 버튼 클릭 | 눌림 애니메이션, 색 순환, 클릭음 | 영향 없음 |
| 정상, 슬라이더 드래그 | 손잡이 이동, 끄는 소리 ('철컥' 없음) | 영향 없음 |

| 고장, 목표 미달성 조작 | 위와 같음 (+ B는 범위 진입 시 '철컥') | 영향 없음, 알림 없음 |
| 고장, 목표 달성 | 마지막 조작의 반응 뒤 **장치 초기화** (A 전부 회색, B 전부 기본값 + 드래그 종료, C 없음) | 정상 복귀, 알림 한 번 → 패널 초록 |
| 고장 발생 | 장치는 현재 상태 유지. 목표만 새로 생긴다 (A 가이드 표시) | 고장 |

## 8. 작업 순서

1. `Facility` 기반 클래스 : `isFault` 필드, `IsFault / MakeFault / Clear` 공통 구현, `OnDeviceChanged`, 추상 훅 3개
2. `FacilityA` : `isFault` 필드 제거, 훅 구현, 버튼 클릭 → `OnDeviceChanged`, 목표 중복 방지, `16` 제거
3. `FacilityB` : `isFault` 필드 제거, 훅 구현, 값 변경 → `OnDeviceChanged`
4. `FacilityC` : `isFault` 필드 제거, 훅 구현, 당김 → `OnDeviceChanged`
5. `IDraggable.IsDragging`, `FacilitySlider.IsDragging`, `FacilitySlider.EndDrag`의 `OnValueChanged` 제거, `FirstPersonController.UpdateDrag` 확인 추가
6. `FacilityManager.OnFacilityInteracted`에서 `Clear()` 제거
7. 컴파일, 씬 · 프리팹에서 `isFault` 값이 이어지는지 확인 (인스펙터 Observation)
8. 9장 완료 기준 확인
9. 규칙 문서 갱신 (12장)

## 10. 결정 사항 (기본안)

| # | 항목 | 기본안 |
| --- | --- | --- |
| D1 | 고장 판정 | **기반 클래스의 고장 플래그 + 템플릿 메서드** (3장). 설비마다 플래그를 따로 두지 않는다 |
| D2 | 알림 시점 | **수리 완료 때 한 번만.** 고장 중 목표 미달성 조작, C의 실패한 당김은 알리지 않는다. 지금 이 알림을 받아 하는 일은 패널 다시 칠하기뿐이고, 상태가 바뀔 때만 필요하다 |
| D3 | 초기화 시점 | **수리 즉시.** 맞춘 형태를 잠깐 보여 준 뒤 초기화하는 지연은 두지 않는다. 필요하면 기반 클래스에 `resetDelay`를 추가한다 |
| D4 | 수리 순간의 드래그 | **장치가 드래그를 끝내고, 컨트롤러가 `IDraggable.IsDragging`으로 알아챈다** (5장 방안 A) |
| D5 | 정상 상태 조작 | **장치는 반응(움직임, 색, 소리), 설비는 무시.** 목표가 없으므로 B의 '철컥'은 나지 않는다 |
| D6 | `FacilitySlider.EndDrag`의 `OnValueChanged` | **지운다.** 값이 바뀌지 않았으므로 알릴 이유가 없다 |
| D7 | 수리 후 초기화 주체 | **설비 자신.** `FacilityManager`는 `Clear()`를 부르지 않는다. `Clear()`는 재시작용으로 남긴다 |
| D8 | `OnFacilityInteracted(bool, int)` | **시그니처 유지.** bool은 항상 false가 되지만, 이벤트 이름 · 형태 정리(「코드 구조 분석」 12장 문제 17, 18)는 따로 한다 |

## 11. 주의 사항
- **고장 발생 때는 장치를 초기화하지 않는다.** 「게임 진행 규칙」 7장 "고장이 나도 장치는 현재 상태를 유지한다"는 그대로다. 초기화는 수리 완료 때만 한다.
- 인스펙터에서 `isFault`를 직접 켜면 목표 없이 고장이 된다. B는 목표가 없어 `IsGoalReached`가 영원히 false이므로 수리할 수 없다. 테스트는 `MakeFault()`로 한다.
- `FacilityManager.OnFaultMade`(임시 코드)가 이미 고장인 설비를 고르는 일은 지금 흐름상 없다 (고장 중에는 진행도가 멈춰 고장 이벤트가 오지 않는다). 그래도 `MakeFault()`가 이미 고장이면 무시하므로 목표가 덮어써지지 않는다.
